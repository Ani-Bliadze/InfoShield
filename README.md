# InfoShield

A **media-literacy layer** for social feeds. InfoShield adds calm, educational
context that explains *how* a post tries to influence you — and **never hides,
blurs, removes, or down-ranks anything**. No accounts, no tracking, no author
profiling. Classification is **content-only and author-agnostic**.

This repo is a complete local-first demo:

- **Landing page** (`/`) — a minimal dark hero: what InfoShield is plus a single
  **Activate** button that saves your feed's URL.
- **Social mock site** (`/social`) — a realistic X/Twitter-style feed with **no
  InfoShield branding of its own**; only the extension adds overlays (and the
  Insights widget appears once the extension reports its scan).
- **Chrome MV3 extension** — injects InfoShield overlays on the localhost feed and
  reports its page scan back to the site's Insights widget.
- **Python/Flask backend** — **cache-first** server, local hate-speech classifier,
  Gemini educational analysis, caching, and the activation config.

## ✅ Manual Steps (only you can do these)

For a **normal demo run you do NOT need a model download, a Gemini key, or any
API calls** — the shipped `cache.json` is served as-is (zero cost). You only need
steps 1–3:

1. **Load the unpacked extension in Chrome** (one-time)
   - Open `chrome://extensions`
   - Toggle **Developer mode** (top-right) **on**
   - Click **Load unpacked** → select the **`extension/`** folder in this repo

2. **Activate InfoShield from the landing page**
   - Open `http://localhost:5173/`
   - Click **Activate**, keep the default `http://localhost:5173/social?bare=1`
     (or enter another **localhost** URL), click **Save target**

3. **Refresh the target page**
   - Open / refresh `http://localhost:5173/social?bare=1`
   - The extension reads your saved target, injects the overlays, and the
     right-rail **InfoShield Insights** widget appears with the live scan.

### Optional — re-analyze with the live model + Gemini

Only needed if you want to regenerate `cache.json` from the real pipeline (this
is the only thing that costs API calls):

1. **Add your key:** `cp .env.example .env` then set
   `GEMINI_API_KEY=...` (https://aistudio.google.com/apikey).
2. **(Online, one-time) Download the model:**
   `.venv/Scripts/python.exe backend/scripts/download_models.py`
3. **Rebuild:** `curl -X POST http://localhost:5050/rebuild-cache` (the social
   site stays clean of any InfoShield controls). Results are live immediately,
   no restart.

## Quick start (commands)

You need **two terminals** (backend + frontend). The existing `.venv` is reused.

**Terminal 1 — backend** (`http://localhost:5050`)

```bash
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt   # first run
.venv/Scripts/python.exe backend/app.py
```

> The backend starts in **cache-first** mode and serves the shipped cache
> instantly — it does **not** need torch/Gemini just to run the demo. Those are
> imported lazily only when you hit `/classify`, `/analyze`, or rebuild the cache.

**Terminal 2 — frontend** (`http://localhost:5173`)

```bash
cd frontend
npm install        # first run
npm run dev
```

Then visit:

| Route | What |
|---|---|
| `http://localhost:5173/` | Landing page + activation flow |
| `http://localhost:5173/social?bare=1` | The demo feed. The site renders a plain feed; the **extension** adds all InfoShield overlays. This is the activation target. |

There is no native, site-rendered InfoShield UI mode — overlays come only from
the extension. Every post carries a stable `data-post-id` for it to find.

## Cache-first + live rebuild

- **Normal demo run:** just start the backend and frontend. `cache.json` is
  served as-is. **No classifier load, no Gemini calls, no API cost.**
- **To re-analyze with the live model + Gemini:** `POST /rebuild-cache`. This
  classifies every post locally, calls Gemini for analysis on flagged posts, and
  overwrites `cache.json`. It is the **only** path that incurs API cost.
- **After a rebuild the new results are live immediately — no restart needed.**
  The endpoint updates the in-memory cache; refresh the feed page so the
  extension re-injects with the new data.

```bash
# Live rebuild against the running backend:
curl -X POST http://localhost:5050/rebuild-cache

# Equivalent offline script (writes cache.json directly):
.venv/Scripts/python.exe backend/scripts/build_cache.py

# Re-author the post set (content only — does not analyze):
.venv/Scripts/python.exe backend/scripts/seed_demo.py

# Smoke-test the classifier device/labels/accuracy on probes:
.venv/Scripts/python.exe backend/scripts/evaluate.py
```

## Run fully offline (after setup)

The shipped `cache.json` is generated by the real pipeline, so the demo is
offline-ready out of the box:

- Backend serves `backend/data/cache.json` from disk (cache-first) — no model,
  no network.
- Frontend is a local Vite app; the extension talks only to `http://localhost:5050`.
- Gemini is **never** called at serve time — only during a rebuild.

(Only a **rebuild** needs the model downloaded and the internet on.)

## Models & thresholds

- Primary classifier: `cardiffnlp/twitter-roberta-base-hate-latest`
- Fallback classifier: `Hate-speech-CNERG/dehatebert-mono-english`
- `FLAG_THRESHOLD = 0.60`, `HIGH_CONFIDENCE = 0.80`
- Confidence phrasing: `≥0.80 → "Detected with NN% confidence"`,
  `0.60–0.79 → "May contain indicators (NN% confidence)"`
- Analysis model: `gemini-3.5-flash` (structured JSON, text-only — author
  metadata is never sent).

The classifier prefers CUDA and falls back to CPU with a logged warning. On
startup it runs a warmup inference and **three label-mapping sanity probes** so
an inverted label map fails loudly.

## Privacy by design

- Only post **text** is ever classified or sent to Gemini.
- No usernames, handles, avatars, or follower data influence analysis.
- No accounts, no telemetry, no tracking, no author profiling.
- Nothing is hidden, blurred, removed, or ranked — InfoShield only **adds** context.
- Extension permissions are limited to `storage` + `http://localhost/*` and
  `http://127.0.0.1/*`.

## Demo feed content

`backend/data/posts.json` is a realistic mixed feed of **19 posts**: ~7 ordinary
posts (jokes, life updates, hot takes), ~7 manipulation posts (fear/urgency,
false scarcity, us-vs-them, conspiracy-adjacent), and ~5 hate-speech posts
(synthetic, **unnamed/fictional groups only** — never real ethnic, religious, or
national groups). It includes the edge cases: a borderline post, a sarcastic
post, a very short post, a long post, and an emoji+URL post.

The shipped `cache.json` is generated by the **real pipeline** (`build_cache.py`).

## Known classifier edge cases (honest notes)

- **The primary model is a *hate-speech* classifier, not a general manipulation
  detector.** Verified on this exact feed: it flags the dehumanizing/exclusionary
  hate posts with high confidence (**4 of 19** flagged, ~0.93–1.00) and leaves
  the manipulation and ordinary posts unflagged. That is correct behavior — a
  hate model is not meant to fire on fear/urgency framing. By design, the local
  model **gates hate**, and **Gemini explains the technique** on flagged posts.
- **Coded / metaphor-only hate is under-detected.** Phrases like *"parasites"* or
  *"animals"* alone score low (~0.05–0.35); the model fires reliably when
  dehumanization is paired with an exclusion/removal cue (*"send them back"*,
  *"driven out"*). The deliberately subtle post (`p19`) stays unflagged — a
  realistic illustration of the model's blind spot.
- **Sarcasm, very short posts, and quoting** carry little hate signal and are
  generally not flagged (the model judges text, not intent).
- If you want manipulation posts flagged too (not just hate), that needs a
  manipulation/persuasion model or a Gemini-based gate — intentionally out of
  scope here, since flagging is the local hate model's job.
- The right-rail **InfoShield Insights** widget is now driven by the extension's
  live page scan (it stays hidden until the extension reports results). The
  honest API view of the same numbers is in `GET /stats`.
